# ToneRelay Installation Prompt

Read this English version in full; a Chinese version is provided separately.

Please enable ToneRelay for Lightroom Classic in the current Agent client. First determine whether to reuse an existing installation, connect only the current client, or perform a fresh installation, repair, or an upgrade I have explicitly requested; perform only the necessary steps.

First identify the operating system, current client, Lightroom Classic, and any ToneRelay components already on this computer. Prefer reading the existing installation's manifest, source, and pinned version. When adding only a client, a verified local installation does not need to be downloaded again just to connect it. If its source or version cannot be verified, report that first; do not assume the shared Runtime is usable based on a directory name or an installed Codex Plugin. When a fresh download, repair download, or upgrade is necessary, use the official public MCP source repository at https://github.com/ReefRuan/tonerelay-lightroom-mcp or its official Gitee source fallback below. This is a source preview installable from a pinned source version, not a claim that stable installers have been released or all platforms have passed acceptance checks. Verify the repository's identity, public access, full commit (resolve and verify a tag's full commit), and that version's INSTALL.en.md. Do not treat the changing main branch as a version number. If no pinned source version can be verified, stop the installation-download branch and report it; reading documentation or verifying and reusing a healthy local installation can still continue. Do not default to internal source code or a private repository. Use local development source only after I explicitly identify its path and authorize a development installation or reuse, and label it as a development build.

Before installing, read the complete FAQ obtained with this prompt. In the MCP source repository root, read `INSTALL-PROMPT.en.md`, `FAQ.en.md`, and the platform installation guide `INSTALL.en.md`; in Portal, the corresponding documents are `docs/install-prompt.en.md` and `docs/faq.en.md`. If the copied content already includes the FAQ body, read it in full; otherwise open the FAQ from the same documentation snapshot rather than assuming it was appended. The MCP repository includes synchronized copies of the public prompt and FAQ, so a complete source download can be read locally without reaching Portal again. If an older source version lacks these files, obtain the official Portal documents separately and record their full commit, while following the target source version's INSTALL.en.md and actual capabilities.

The two source pairs have different roles. Complete MCP installation source and its bundled installation prompt and FAQ: primary https://github.com/ReefRuan/tonerelay-lightroom-mcp , official fallback https://gitee.com/ReefRuan/tonerelay-lightroom-mcp . Portal maintains the website, style resources, and public installation documents: primary https://github.com/ReefRuan/tonerelay-portal , official fallback https://gitee.com/ReefRuan/tonerelay-portal . A Portal download cannot replace the MCP installation source. If GitHub fails, times out, or is interrupted, use the corresponding Gitee repository for complete source at the same pinned full commit or documents at the same path. Verify the official owner, public access, pinned commit, and file integrity. Mirrors may lag; do not assume they are the latest or mix installers, Skills, plug-ins, and Runtime files from different commits. If only the mirror is reachable from the outset, report its URL, the selected full commit, and the available verification evidence, then follow that version's installation instructions; live GitHub access is not a prerequisite. If provenance or integrity cannot be verified sufficiently, stop the installation-download branch and report it rather than switching to internal or unverified third-party sources. Raw document URLs can use the selected repository's `/raw/<full-commit>/<file-path>`, for example `FAQ.en.md` in MCP or `docs/faq.en.md` in Portal.

A source fallback is not a dependency fallback. Check Python/pip network access separately. If PIP_INDEX_URL is needed, use only a verified trusted HTTPS index, scope it to the installation process or dedicated environment, and record the choice; do not silently change global configuration or disclose index credentials. Keep TLS certificate verification enabled. Do not bypass failures with --trusted-host, disabled verification, or packages of unknown origin. If verification is impossible, report the dependency stage as incomplete rather than repeatedly reinstalling.

Use only entry points supported by the current operating system and pinned version. Do not assume macOS commands, installation manifests, or uninstall safeguards apply to Windows; clearly identify any platform capability that has not been verified.

If an installation already exists, first perform read-only checks of the shared Runtime, stable MCP launcher, Bridge, the version/build actually loaded by the Lightroom plug-in, and the current Catalog's identity, mode, and authorization. If the source can be verified, the version is compatible with the current client, the shared components are healthy, and this task only connects another Agent client: reuse the existing installation root, configuration, data, and Catalog authorization. Do not download the complete distribution again, run `prepare` or the Runtime's `install`, rebuild dependencies, register or restart the Lightroom plug-in again, or change the shared mode, binding, or other clients. Only add or repair the current client's ToneRelay MCP/Plugin connection through that client's official entry point. If the client supports Skills, deliver the startup Skill from the verified source of the same version; do not silently overwrite a copy the user has modified. Complete the necessary client trust confirmation, record the client using the method supported by the current version, and then verify tool discovery, the Skill (if supported), read-only health checks, current photo selection, and the actual launcher/version/paths in a real new session in that client. `record-client` only records client configuration that has already been completed; it does not establish the connection itself. Seeing that the old client works does not replace acceptance checks in the new client.

If shared components are missing, incompatible, or fail a health check, first report the specific evidence. Repair only the affected layer and perform the subsequent acceptance checks; do not upgrade incidentally just because a client is being added. If changes to the shared Runtime, Bridge, Lightroom plug-in, Catalog mode, or binding are genuinely necessary, first list the impact on other clients and obtain the corresponding authorization. Reuse existing authorization for the same Catalog and mode without asking to bind again.

After verifying the source and choosing the branch above, this authorization covers only the ordinary downloads, dependency installation, the current client's ToneRelay entry and Skill connection, Lightroom plug-in registration/enabling, and normal restarts required by that branch. Adding a client to a healthy installation does not authorize reinstalling or upgrading shared components. Continue the necessary steps under the existing authorization; do not stop after writing configuration or preparing a plan. Preserve other MCP entries, photos, Catalogs, presets, and my personal data.

First tell me in the client which reuse or installation path, source version, and branch will be used. Then automatically complete the ordinary steps in that branch without requiring an additional reply to approve the default path. To locate Lightroom, check only system application registration, standard installation locations, and running processes; do not search the disk for the application. If a valid plug-in response already exists, continue without searching for the application just to confirm its installation location. If Lightroom needs to be opened but its location cannot be found, or it is confirmed not to be running, ask directly in the current client: “Please manually open Lightroom Classic and the Catalog you want to use, then reply ‘Opened’.” Use the client's question capability; if no question tool exists, ask directly in the conversation and wait. While waiting, continue any downloads, dependency preparation, or client connection required by the current branch. After the reply, resume connection verification. Do not treat “application location not found” as an installation failure, and do not repeatedly search or probe. A probe timeout alone does not prove that Lightroom is not running.

For a first installation, use `full` by default; do not create a separate Sandbox just for acceptance checks. If the current Catalog is not bound, show its actual detected name and mode in the current client and ask: “The current Catalog is ‘<actual name>’ and is not yet bound; the access mode is <actual mode>. Bind this Catalog and allow ToneRelay to operate on it? Reply ‘Bind’ to continue.” After the user replies “Bind”, probe again and verify that this is still the Catalog just shown. Then use that version's confirmation tool to save its identity and the plug-in's actual mode, read the authorization back, and continue. Do not bind automatically without a reply, and do not stop after merely reporting that authorization is missing. If the name or identity is unknown, first ask me to open the target Catalog; do not guess. Reuse explicit existing authorization for the same Catalog and mode without asking again. `full` still retains Catalog identity checks, virtual copies for editing, and tool execution restrictions.

Also compare the plug-in's actual mode with the Runtime's saved expected mode. If the identity is unchanged, the plug-in is already in `full`, but the Runtime still expects `safe`, show the current Catalog name and both modes, then ask directly: “Bind this Catalog and keep its current full mode? Reply ‘Bind’ to continue.” If the same authorization already exists, use the confirmation tool directly to save the actual mode and read health; do not make me switch back and forth in Plug-in Manager. If the identity differs, show the new target and explicitly ask whether to rebind. If the tool does not support this, explain the actionable next step; do not edit the identity by hand or silently rebind. During upgrades and repairs, “new installations default to full” is not authorization to overwrite an existing choice of safe mode.

Before the first download or Git checkout, establish a single root directory for all ToneRelay-owned files. For a new macOS installation, use `~/Library/Application Support/ToneRelay`. On Windows, use the dedicated root supported by the pinned version, `%SystemDrive%\ToneRelay` by default; if it is not writable, use `%LOCALAPPDATA%\ToneRelay` only as allowed by that version's instructions, and record the choice. Do not use an existing development repository or any of its subdirectories as the installation root, data root, download directory, or cache directory. Even for an explicitly authorized development installation, read only the specified source and place the installed copy in the dedicated root. A development repository is not owned by the installer or uninstaller.

This root covers all ToneRelay-owned files during installation and subsequent operation: downloads and source copies, MCP launcher, Runtime, dedicated interpreter or virtual environment and dependencies, Lightroom plug-in copy, runtime configuration and state, Catalog binding records, Episodes, preview and render outputs, queues and staging, logs, caches, temporary files, backups, and installation manifest. On macOS, use the single `config.json` under the installation root to manage paths, targets, presentation, folders, execution, and bridge; `TONERELAY_CONFIG` only locates this file. Data defaults to `data` within the root, and cache and temporary directories default to `cache`/`tmp`. A new installation must not read or migrate old scattered configuration or silently adopt external legacy data directories. Verify that MCP, Bridge, and diagnostic subprocesses use the same configuration.

Cache and temporary-directory containment must cover the full lifecycle. According to the actual tools and platform support, point the pip cache, Python/dependency caches, and temporary files into the root, for example `<installation-root>/cache` and `<installation-root>/tmp`. Check `PIP_CACHE_DIR`, `PYTHONPYCACHEPREFIX` for Python bytecode, `XDG_CACHE_HOME` for dependencies that support XDG, `TMPDIR` on macOS or `TEMP`/`TMP` on Windows, and any other cache settings the dependencies actually use. The dedicated macOS launcher generates these environment settings from config.json on every launch, so installation, repair, Bridge, MCP instances newly started by clients, and their subprocesses continue to inherit them. Register the stable launcher in clients rather than copying business configuration into client configuration again. Handle Windows according to that version's capabilities. Setting these variables only once in the installation terminal is not sufficient. Give the dedicated launcher a working directory inside the root, and check that client/parent-process environments do not override data, cache, or temporary paths back outside the root. Do not globally change cache directories for the system or other applications, and do not assume every dependency follows the same variable. Verify actual working directories and file-write locations; after resolving symbolic links, owned files must still reside within the installation root.

Host-required client configuration, plug-in registrations/managed links, and Lightroom preferences remain in their host locations. Record each path, target, ownership, and uninstall action individually. Client-managed session logs, system logs, and shared interpreters belong to their hosts or shared components. Photos, the main Catalog, user presets, and final export locations explicitly chosen by the user are not ToneRelay-owned files. Keep configuration separate from ownership records: config.json stores settings only; install-manifest.json records ownership and progress. Using the installation manifest supported by that version, continuously record the source version, actual installation/data/cache/temporary paths, client connections, external registrations, process ownership, and completed items. If that version does not support a manifest, keep path and progress records under the installation root; do not assume new commands exist.

If the pinned version supports macOS `prepare`, `paths`, and `record-client`, use them to initialize the unified configuration, read actual directories, and record host client configuration. Place installation sources inside the root's configured downloads directory. Verify that commands exist before using them; do not treat an implementation in development source as a released capability.

An upgrade primarily installs the verified newer software and updates the ToneRelay launch entry points and plug-in copy, while retaining the recorded installation and data locations. A fresh installation uses the new version's default configuration without reading or merging old scattered configuration. An upgrade preserves the currently valid unified configuration and data; do not proactively develop compatibility, migration, or merge schemes for old versions. Handle only old ToneRelay processes or registration entries that actually prevent the new version from starting, according to their actual ownership; do not clean unrelated directories. If the existing layout blocks the new installation, explain the specific reason and smallest corrective action. Obtain authorization before moving personal data. On completion, list the pinned source version, Runtime status, and the version/build actually loaded by the Lightroom plug-in; updated files do not prove that the running version has been updated.

For a fresh installation, repair, or authorized upgrade, execute and verify steps 1–5 layer by layer. When adding only a client, reuse the verified shared components above and skip unnecessary downloads and reinstalls, but still perform steps 6–7 and record the actual results:

1. Download or check out the verified pinned version into the directory above. An official ZIP is also acceptable; do not require Git to be installed first. Record the version, source, and integrity-verification results. If the distribution does not support an installation manifest, truthfully record the paths instead of assuming new commands exist.
2. Verify that the actual interpreter can start independently and import required dependencies, and perform pip check or an equivalent dependency check as directed by the release instructions.
3. Verify that the launcher starts, MCP initialize succeeds, and the tool list and schemas can be read.
4. Call the Bridge's read-only health check and verify the Lightroom plug-in's actual response. A running Runtime process is not proof that the plug-in is connected.
5. Verify the actual registered Lightroom plug-in path, enabled state, and loaded version. When an update is needed, quit normally and reopen Lightroom.
6. Verify tool discovery and read-only calls in a real new client session. If the client supports Skills, also check that the startup Skill is actually visible. Connect each client only according to that product's current official instructions: Codex Plugin, WorkBuddy MCP, Kimi Work, and Kimi Code CLI are not interchangeable.
7. After this connection or installation, and again after a real new client session starts, check the actual launcher/interpreter, MCP and Bridge data roots, working directories, cache/temporary settings, and files created by this task. Compare them item by item with the installation manifest and list all external host registrations and shared components. Configuration text, directory names, or environment values visible only in an old terminal cannot prove ownership. Mark unobservable paths or writes as pending verification; do not claim that “all data is in one directory.”

If the Catalog is not yet bound, first obtain authorization and complete the binding in the current client using the process above. Reuse explicit existing authorization for the same Catalog and mode without rebinding. Then actually create a new session in the current client, submit a read-only verification request, and check whether ToneRelay tools are visible and whether health checks and current-photo readback succeed. The new session must only read back the actual mode, saved expected mode, and authorization result; all three must agree for acceptance to pass. Do not bind, modify photos or Catalog contents, or disable safeguards during read-only acceptance. Starting a process or checking an old session does not replace acceptance in a new session.

After a first installation passes acceptance, offer once: “If needed, I can help back up the current Catalog.” Do not repeat this offer when only adding a client. This is an optional follow-up that does not block use; do not automatically copy or switch Catalogs. If the user agrees, prefer helping with Lightroom's built-in Catalog backup. Before making a manual copy, save work and quit Lightroom normally, retain `.lrcat` and any existing `.lrcat-data`, and verify that the backup is usable. Explain that Catalog backups do not include original photos. Personal backups are not files ToneRelay may uninstall.

If a system password, login, terms of service, or a tool explicitly requires the user's own confirmation, explain the exact blocked action, its reason, and the minimum action I need to take, and save progress. If you cannot create or observe a new session, provide a copyable read-only verification request and a checkpoint handoff, mark verification as pending, and do not declare success. On completion, list actual evidence and anything that remains unverified.
